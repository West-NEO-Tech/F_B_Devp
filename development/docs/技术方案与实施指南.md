# 05 - 技术方案与实施指南

## 1. 技术基线：MiroFish + OASIS

### 1.1 现有架构回顾

MiroFish（https://github.com/666ghj/MiroFish）的五阶段管线：

```
Seeds → Graph Builder → Profile Generator → Simulation Runner → Report Agent → Interactive
```

对应源码结构：

```
MiroFish/
├── backend/
│   ├── graph_builder.py          # 阶段1：知识图谱构建
│   ├── oasis_profile_generator.py # 阶段2：Agent人设生成
│   ├── simulation_runner.py       # 阶段3：模拟执行（调用OASIS）
│   ├── report_agent.py            # 阶段4：报告生成（ReACT模式）
│   └── ...
├── frontend/                      # Vue.js 3 + Vite 前端
└── .env.example                   # API 配置
```

底层仿真引擎依赖 **OASIS**（https://github.com/camel-ai/oasis）：
- PettingZoo 风格接口
- 双平台模拟（Twitter / Reddit）
- 23 种 Agent 动作（发帖、评论、点赞、关注等）
- 推荐算法将交互量从 O(n^2) 降到 O(n*k)

### 1.3 Agent-Kernel 技术参考

Agent-Kernel（https://github.com/ZJU-LLMs/Agent-Kernel ）是浙大 ZJU-LLMs 团队的开源大规模 Agent 仿真框架，Apache-2.0 许可，Python ≥ 3.11，已在万人规模校园模拟中验证。其微内核 + 插件架构对 BizSim 的引擎设计有重要参考价值。

**核心架构**：

```
┌─────────────────────────────────────────────────────────────┐
│                      PodManager (分布式)                     │
│    • 按 pod_size 切分 Agent 到多个 MasPod                    │
│    • asyncio.gather 并行调度所有 Pod                         │
├─────────────────────────────────────────────────────────────┤
│  MasPod (Ray Actor)    MasPod (Ray Actor)    MasPod ...     │
│  ┌─────────────────┐  ┌─────────────────┐                   │
│  │ AgentManager    │  │ AgentManager    │                   │
│  │  ├─ Agent 1     │  │  ├─ Agent 6     │                   │
│  │  ├─ Agent 2     │  │  ├─ Agent 7     │                   │
│  │  └─ ...         │  │  └─ ...         │                   │
│  │ Controller      │  │ Controller      │                   │
│  │ Environment     │  │ Environment     │                   │
│  │ AsyncModelRouter│  │ AsyncModelRouter│                   │
│  └─────────────────┘  └─────────────────┘                   │
├─────────────────────────────────────────────────────────────┤
│  System: Timer │ Messager │ Recorder │ DB Adapters          │
└─────────────────────────────────────────────────────────────┘
```

**模拟主循环**（源码 `run_simulation.py`）：

```python
for tick in range(max_ticks):
    await controller.step_agent()                       # 所有 Agent 并行执行一个 tick
    await system.run("messager", "dispatch_messages")   # 消息分发
    await controller.update_agents_status()             # 状态更新钩子
    await system.run("timer", "add_tick", duration)     # 推进时钟
```

**Agent 认知管线**（源码 `agent.py`）：每个 Agent 每 tick 执行 5 个组件，**组件间串行、Agent 间并行**：

| 组件 | LLM 调用 | 说明 |
|------|---------|------|
| perceive | 无 | 收集环境观察 + 消息 |
| plan | **1 次** | LLM 规划下一步动作（~250-600 tokens/次） |
| invoke | 无 | 执行动作（移动、发消息、调 MCP 工具） |
| state | 无 | 更新 Agent 内部状态 |
| reflect | **0-1 次** | 条件触发的反思（可选） |

**并行模型**：

| 维度 | 单机模式 (standalone) | 分布式模式 (distributed) |
|------|---------------------|------------------------|
| Agent 间并行 | `asyncio.gather` | Ray Actor + `asyncio.gather` |
| Agent 内 | 5 组件串行 | 同左 |
| Pod 间并行 | N/A | `asyncio.gather(*[pod.forward.remote(...)])` |
| LLM 路由 | `aiohttp.ClientSession` | 每 Pod 独立 `AsyncModelRouter` |
| 可扩展性 | 单进程 + API 限速瓶颈 | 多机线性扩展 |

**关键特性**（与 BizSim 相关的）：

- **Snapshot / Rollback**：`controller.make_snapshot()` 和 `rollback_to_tick(tick)` 支持模拟状态保存与回滚，可实现"分支模拟"和"what-if 分析"
- **运行时动态增删 Agent**：`agent_manager.add_agent()` / `remove_agent()` 支持模拟过程中动态调整 Agent 群体
- **数据库持久化**：支持 PostgreSQL / Milvus / Redis，每组件可独立 `save_to_db` / `load_from_db`
- **MCP 工具集成**：Action 层的 `MCPToolPlugin` 可直接连接 MCP 服务器，为 Agent 提供外部工具
- **插件化组件**：Agent 的每个认知步骤（perceive/plan/invoke/state/reflect）和 Action 都是独立插件，YAML 配置驱动
- **Hook 系统**：`ModelRouter` 的 `HOOK_POST_CHAT` / `HOOK_ON_ERROR` 可精确追踪每次 LLM 调用的 token 消耗

### 1.4 三引擎对比分析

| 维度 | OASIS (CAMEL-AI) | MiroFish (666ghj) | Agent-Kernel (ZJU) |
|------|-----------------|-------------------|-------------------|
| **定位** | 社交平台大规模仿真引擎 | 端到端舆情/文学模拟平台 | 通用大规模 Agent 仿真框架 |
| **许可** | Apache-2.0 | AGPL-3.0 | Apache-2.0 |
| **语言** | Python | Python (Flask) | Python ≥ 3.11 |
| **架构** | PettingZoo 接口 + 推荐算法 | 5 阶段管线（封装 OASIS） | 微内核 + 插件 + Ray 分布式 |
| **模拟模型** | 同步 tick + 推荐算法选交互对 | OASIS 引擎 + 知识图谱增强 | 同步 tick + 认知管线 |
| **Agent 间并行** | asyncio | asyncio (via OASIS) | asyncio + Ray Actor |
| **Agent 内流程** | 单步 action | 单步 action | 5 组件管线 (perceive→reflect) |
| **交互优化** | O(n×k) 推荐算法 | 继承 OASIS | O(n) 全并行 (无推荐算法) |
| **LLM/Agent/tick** | 1 次 | 1 次 | 1-2 次（plan + 可选 reflect） |
| **持久化** | 无 | 文件存储 | PostgreSQL / Milvus / Redis |

| **动态 Agent** | 无 | 无 | ✅ 运行时增删 |
| **工具集成** | 23 种社交动作 | 继承 OASIS + ReACT 报告工具 | MCP 协议 + 自定义 Action 插件 |
| **已验证规模** | 数千 Agent | 数百 Agent | 10,000 Agent（ZJU 校园实验） |
| **报告生成** | 无 | ✅ 内置 ReACT Report Agent | 无 |
| **知识图谱** | 无 | ✅ Zep Cloud GraphRAG | 无 |

**对 BizSim 的启示**：

1. **引擎选型**：MVP 阶段仍以 OASIS 为基础引擎（与 MiroFish 管线兼容、推荐算法降低交互成本），但 Agent-Kernel 的**微内核插件架构**和**分布式能力**是长期演进方向。
2. **短期复用（P1）**：OASIS 的推荐算法（O(n×k)）在 200 Agent 量级直接降低 LLM 调用量；MiroFish 的 5 阶段管线提供完整的产品流程参考。
3. **中期增强（P2-P3）**：参考 Agent-Kernel 的 Hook 系统实现精确的 token 追踪和成本控制；参考其 snapshot/rollback 实现"what-if 分支模拟"。
4. **长期演进（P4+）**：如需支撑 500+ Agent 的 Enterprise 模式，可迁移至 Agent-Kernel 的 Ray 分布式架构；其 MCP 集成能力可对接外部数据源（ABS 统计、Crunchbase 等）。
5. **许可优势**：Agent-Kernel 采用 Apache-2.0，无 AGPL 传染风险，是比 MiroFish 更安全的长期选择。

### 1.5 三引擎 Agent 间信息传导机制对比分析

基于 Agent-Kernel（`messager.py`、`pod_manager.py`、`controller.py`、`mas_pod.py`）、OASIS（`channel.py`、`platform.py`、`recsys.py`、`env.py`）和 MiroFish 源码的逐文件追踪，分析三引擎在并行/分组场景下 Agent 间信息如何传导、跨组上下文如何维护、以及存在哪些瓶颈。

#### 1.5.1 Agent-Kernel：集中式 Messager + 全局路由表（BSP 模型）

**完整消息传递路径**（源码级追踪）：

```
Agent A (Pod 1)                                        Agent B (Pod 3)
     │                                                       ▲
     ▼                                                       │
CommunicationPlugin.send_message()                           │
     │                                                       │
     ▼                                                       │
System.run("messager", "send_message", msg)                  │
     │                                                       │
     ▼                                                       │
┌──────────────────────────────────────────┐                  │
│  Messager (@ray.remote 单例 Actor)       │                  │
│  message_queue: asyncio.Queue[Message]   │                  │
│  ┌─────────────────────────────────┐     │                  │
│  │ dispatch_messages():            │     │                  │
│  │   dequeue → 过滤 → 路由分发     │     │                  │
│  └─────────────────────────────────┘     │                  │
└──────────────────────────────────────────┘                  │
     │                                                       │
     ▼                                                       │
PodManager.deliver_message.remote(to_id, msg)                │
     │ _agent_id_to_pod[to_id] → Pod 3                       │
     ▼                                                       │
Pod3.forward.remote("deliver_message", to_id, msg)           │
     │                                                       │
     ▼                                                       │
Controller.deliver_message() → AgentManager → Agent B  ──────┘
```

**关键设计**：

| 特性 | 实现 | 源码位置 |
|------|------|---------|
| **同步模型** | BSP（Bulk Synchronous Parallel）：全部 Agent 完成 tick → 屏障 → 消息分发 → 下一 tick | `run_simulation.py` 主循环 |
| **全局路由表** | `PodManager._agent_id_to_pod: Dict[str, MasPod]` — Agent ID → 所属 Pod 的映射 | `pod_manager.py` |
| **集中式消息队列** | 唯一的 `Messager` Ray Actor，所有 Pod 的消息汇总到此 | `distributed/messager.py` |
| **消息过滤** | blocked_senders/receivers/pairs、allow_kinds、blocked_keywords/regex | `messager.py` `_apply_filters()` |
| **跨 Pod 方法调用** | `controller.run_agent_method()` 优先本地查找，未找到则 `pod_manager.run_agent_method.remote()` | `distributed/controller.py` |

**分组与跨组通信的回答**：即使 1000 个 Agent 分 10 组（10 个 Pod），**任意 Agent 均可向任意其他 Agent 发消息**——PodManager 的全局路由表保证了跨 Pod 投递。分组仅是计算并行的划分单元，而非信息隔离单元。但受 BSP 模型约束，同一 tick 内的消息**不可见**，只有到下一 tick 才能被接收方看到（1-tick 延迟）。

#### 1.5.2 OASIS：平台即中介 + 推荐系统筛选（共享 DB 模型）

**完整信息传导路径**（源码级追踪）：

```
Agent A (发布一条商业观点)              Agent B (看到并回复)
     │                                       ▲
     ▼                                       │
SocialAgent.perform_action_by_llm()          │ SocialAgent.perform_action_by_llm()
     │ LLM输出 tool_call: create_post        │ LLM输出 tool_call: create_comment
     ▼                                       │
SocialAction.create_post(content)            │
     │                                       │
     ▼                                       │
Channel.write_to_receive_queue(action)       │ Channel.read_from_send_queue(msg_id)
     │                                       │         ▲
     ▼                                       │         │
┌──────────────────────────────────────────────────────────┐
│  Platform (异步服务, 单线程事件循环)                       │
│  ┌────────────┐                                         │
│  │  SQLite DB  │ ← 唯一持久化层，所有 Agent 共享         │
│  │  user / post / comment / follow / trace / rec 表     │
│  └────────────┘                                         │
│         │                                               │
│         ▼                                               │
│  ┌──────────────────────────────────────┐               │
│  │  update_rec_table() — 每 tick 调用一次 │              │
│  │  推荐算法: random/reddit/twitter/twhin │              │
│  │  输出: rec_matrix[user_id] = [post_ids]│              │
│  └──────────────────────────────────────┘               │
│         │                                               │
│         ▼                                               │
│  rec 表: user_id → [推荐的 post_id 列表]                 │
│         │                                               │
│         ▼  refresh(agent_id)                            │
│  从 rec 表取 refresh_rec_post_count 条                   │
│  + 从 follow 关系取 following_post_count 条              │
│  → 返回帖子内容 + 评论                                   │
└──────────────────────────────────────────────────────────┘
     │                                       │
     ▼                                       │
Agent B 的环境观测:                           │
  SocialEnvironment.to_text_prompt()          │
  → self.action.refresh() 获取推荐帖子        │
  → 拼接为 LLM 可读的文本 prompt ─────────────┘
```

**关键设计**：

| 特性 | 实现 | 源码位置 |
|------|------|---------|
| **信息中介** | 所有交互通过 Platform + SQLite DB 中转，无 Agent 直接通信 | `platform.py` `running()` |
| **异步通道** | 每个 Agent 拥有自己的 `Channel`（asyncio.Queue + AsyncSafeDict） | `channel.py` |
| **推荐算法** | 4 种可选：random / reddit(热度排序) / twitter(余弦相似度) / twhin-bert(个性化) | `recsys.py` |
| **交互选择** | O(n×k)：每 Agent 每次 refresh 只看 `refresh_rec_post_count`(默认 2) + `following_post_count`(默认 3) 条帖子 | `platform.py` `refresh()` |
| **全局一致性** | 所有 Agent 读写同一个 SQLite DB → 自然的全局一致视图（受 recsys 过滤） | `platform.py` |
| **并发控制** | `OasisEnv.llm_semaphore = asyncio.Semaphore(128)` — 限并发 LLM 请求数 | `env.py` |
| **tick 同步** | `env.step()` → `update_rec_table()` → `asyncio.gather(*tasks)` → `time_step += 1` | `env.py` `step()` |

**分组与跨组通信的回答**：OASIS **不分组**。所有 Agent 在同一个 asyncio 事件循环中并行（受 Semaphore 限制），共享同一个 SQLite 数据库。Agent 之间不直接发送消息——信息传导路径是：Agent A 发帖 → 写入 SQLite → 推荐算法将帖子推给 Agent B → Agent B 下次 refresh 时读到。这意味着：
- **优点**：天然的全局一致性，不存在"分组隔离"问题
- **缺点①**：SQLite 是单写入者（即使 WAL 模式），200+ Agent 高频写入时可能出现锁争用
- **缺点②**：单进程单事件循环，无法利用多核/多机——OASIS 的"百万 Agent"论文标题通过降低 LLM 调用频率（不是分布式计算）实现
- **缺点③**：推荐算法决定了谁看到谁的信息，这是一个**隐式的信息过滤层**——Agent 可能永远看不到与其不相似的观点（信息茧房效应）

#### 1.5.3 MiroFish：继承 OASIS + Zep GraphRAG 知识层

MiroFish 在运行时模拟阶段完全继承 OASIS 的信息传导机制（`simulation_runner.py` 调用 OASIS 引擎）。其独特的信息层在模拟**之前**：

```
Seeds (商业材料)
     │
     ▼
Graph Builder (Zep Cloud GraphRAG)
     │ 构建知识图谱：实体、关系、社区结构
     ▼
Profile Generator
     │ 基于图谱节点生成 Agent 人设
     ▼
Simulation Runner ← 信息传导完全依赖 OASIS
     │
     ▼
Report Agent (ReACT 模式，读取 OASIS 的 SQLite trace 表)
```

**额外的信息传导路径**：Zep GraphRAG 在人设生成阶段将种子材料中的知识"编译"进每个 Agent 的 system prompt，但在运行时模拟中**不参与** Agent 间交互。这意味着 Agent 之间的商业知识仅通过初始人设隐式传递，运行时无法"查询知识图谱"。

#### 1.5.4 三引擎信息传导对比表

| 维度 | Agent-Kernel | OASIS | MiroFish |
|------|-------------|-------|---------|
| **传导模型** | 显式消息传递（Agent→Messager→Agent） | 隐式平台中介（Agent→DB→RecSys→Agent） | 同 OASIS |
| **分组策略** | Pod 划分（可配置 pod_size） | 不分组，全局单进程 | 同 OASIS |
| **跨组通信** | ✅ 全局路由表无障碍投递 | N/A（无分组） | N/A |
| **信息延迟** | 1 tick（BSP 屏障） | 1 tick（update_rec_table + refresh） | 同 OASIS |
| **信息筛选** | 消息过滤器（黑名单/白名单/正则） | 推荐算法（相似度/热度/随机） | 同 OASIS |
| **信息茧房风险** | 低（默认全连接，除非手动过滤） | **中高**（rec 算法偏好相似内容） | 同 OASIS |
| **全局一致性** | 每 Pod 独立 Environment → **需显式同步** | ✅ 全局共享 SQLite | 同 OASIS |
| **写入瓶颈** | 集中式 Messager 单 Actor 队列 | SQLite 单写入 + WAL | 同 OASIS |
| **扩展性** | Ray 多节点线性扩展 | 单机 asyncio 天花板 | 同 OASIS |
| **持久化追溯** | PostgreSQL/Milvus/Redis | SQLite trace 表 | 同 OASIS |

#### 1.5.5 BizSim 的信息传导设计建议

基于上述源码分析，BizSim 在不同阶段应采用不同的信息传导策略：

**MVP 阶段（OASIS 引擎，≤200 Agent）**：
1. **复用 OASIS 的平台中介模型**：商业场景天然适合这种模式——Agent 在"商业论坛"发言、评论、投票，推荐算法将相关讨论推送给合适的角色。
2. **调整推荐算法**：默认的 Twitter 余弦相似度推荐会导致信息茧房。BizSim 应采用**混合推荐**：70% 基于角色关联（消费者看到竞品分析、投资人看到定价讨论）+ 30% 随机打散，确保多元观点交叉。
3. **SQLite 写入优化**：采用 `PRAGMA synchronous = OFF`（OASIS 已默认开启）+ 批量写入 + WAL 模式。200 Agent 量级下 SQLite 尚可承受。

**Enterprise 阶段（Agent-Kernel 引擎，500+ Agent）**：
1. **迁移至显式消息传递**：Agent-Kernel 的 Messager + PodManager 模型支持精确的消息路由，可实现"消费者群组讨论"、"投资人闭门会议"等分组场景，同时保持跨组信息透传能力。
2. **缓解 Messager 单点瓶颈**：500+ Agent 每 tick 产生大量消息时，单一 Messager Actor 可能成为瓶颈。可考虑分片 Messager（按 Pod 分区）或消息批量压缩。
3. **Environment 同步问题**：Agent-Kernel 每 Pod 有独立 Environment，需要设计全局市场状态广播机制（如每 N tick 同步一次宏观指标）。

## 2. 需要改造的核心模块

### 2.1 改造点一：种子材料输入适配

**现状**：MiroFish 的 `graph_builder.py` 接受 PDF/MD/TXT 等长文本种子材料，用于舆情/文学场景。

**改造**：创建 `biz_seed_builder.py`，将用户的结构化商业输入转化为适合图谱构建的种子材料。

```python
# 改造思路（伪代码）
class BizSeedBuilder:
    def build_seed(self, user_input: BizInput) -> str:
        """
        将用户输入的商业参数转化为 graph_builder 可消费的种子文本
        """
        seed = f"""
        ## 商业场景描述
        产品名称：{user_input.product_name}
        产品类型：{user_input.product_type}  # SaaS / App / Marketplace
        一句话描述：{user_input.description}
        目标市场：{user_input.target_market}
        目标用户：{user_input.target_users}
        定价策略：{user_input.pricing}
```

## 5. 大规模 Agent 模拟性能与成本分析

BizSim 的核心卖点是 **数百 Agent 的市场模拟**。本节详细分析大规模运行的性能特征和成本结构，论证"数百 Agent 模拟"在技术和商业上的可行性。

### 5.1 层级化 Agent 架构（Hierarchical Agent Architecture）

参考 OASIS（CAMEL-AI 团队）的层级化社会模拟方法：

```
┌──────────────────────────────────────────────────────────┐
│              全局协调层 (Global Coordinator)              │
│    • 每 N 轮执行一次（N=5~10）                             │
│    • 宏观环境更新：市场趋势、政策变化、季节因素              │
│    • 使用 GPT-4o 级模型                                   │
│    • 复杂度：O(1) per update                              │
└────────────────────┬─────────────────────────────────────┘
                     │
        ┌────────────┼────────────┬────────────┐
        ▼            ▼            ▼            ▼
   ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
   │消费者社区│ │企业客户区│ │竞品+供应│ │投资+专家│
   │ n=80-150│ │  n=20-50│ │  n=10-20│ │  n=5-15│
   │ 每轮交互│ │ 每轮交互│ │ 每轮交互│ │ 每轮交互│
   └────┬────┘ └────┬────┘ └────┬────┘ └────┬────┘
        │           │           │           │
    ┌───┴───┐   ┌───┴───┐   ┌───┴───┐   ┌───┴───┐
    │边缘Agent│ │边缘Agent│ │核心Agent│ │核心Agent│
    │规则引擎 │ │GPT-mini│ │ GPT-4o │ │ GPT-4o │
    └───────┘   └───────┘   └───────┘   └───────┘
```

**交互复杂度优化**：
- 朴素实现：O(n²)（每个 Agent 与所有其他 Agent 交互）
- OASIS 推荐算法：O(n×k)（每个 Agent 只与 k 个相关 Agent 交互，k << n）
- 实际效果：200 Agent 的交互量从 40,000 降到 ~2,000（k=10）

### 5.2 LLM 调用成本精算

**调用模型**：每个 LLM 驱动的 Agent 每轮 1 次调用，输入 ~2,500 tokens，输出 ~200 tokens。（Agent-Kernel 源码实测：plan 组件每次 ~250-600 tokens，见 §5.7 详细验证。）

**三层模型分级策略**：

| 层级 | 占比 | 模型 | 单次调用成本 | 用途 |
|------|------|------|-----------|------|
| 核心层 | 15% | GPT-4o | ~$0.005 | 投资人、竞品核心决策、报告生成 |
| 社区层 | 40% | GPT-4o-mini | ~$0.0005 | 消费者群体交互、企业客户评估 |
| 边缘层 | 45% | 规则引擎 | $0 | 简单消费者反应、统计近似 |

**不同规模的成本计算**：

| 场景 | Agent 数 | 轮次 | LLM 调用次数 | 理论成本 | 优化后成本 | 运行时间 |
|------|---------|------|------------|---------|-----------|---------|
| Quick Scan | 20 | 10 | ~110 | $0.80 | **$0.5-1** | ~3 秒 |
| Standard | 100 | 30 | ~1,650 | $4.50 | **$3-5** | ~10 秒 |
| Deep Dive | 200 | 50 | ~5,500 | $12.00 | **$8-15** | ~1 分钟 |
| Enterprise | 500 | 100 | ~27,500 | $55.00 | **$25-45** | ~2.5 分钟 |

> **计算公式**：LLM 调用数 = (核心占比 × N + 社区占比 × N) × K 轮。边缘层不消耗 LLM。
>
> **优化后成本** 包含 Batch API（-50%）、Prompt Cache（-15%）、语义缓存（-20%）的综合效果。

### 5.3 运行时间分析

基于 asyncio 异步并发、500 并发连接的假设（Agent-Kernel 源码验证了 asyncio.gather 的并发模式，分布式模式可通过 Ray 突破单机瓶颈，详见 §5.7）：

| 并发度 | 100 Agent × 30 轮 | 200 Agent × 50 轮 | 500 Agent × 100 轮 |
|-------|-------------------|-------------------|-------------------|
| 50 并发 | ~30 秒 | ~3 分钟 | ~15 分钟 |
| 200 并发 | ~10 秒 | ~50 秒 | ~4 分钟 |
| 500 并发 | ~5 秒 | ~20 秒 | ~2.5 分钟 |

> **关键结论**：200 Agent × 50 轮的 Deep Dive 模拟，在 200 并发下不到 1 分钟即可完成——远优于"等待数小时"的用户预期。

### 5.4 成本优化策略矩阵

| 策略 | 节省比例 | 实现复杂度 | 优先级 | 说明 |
|------|---------|-----------|-------|------|
| **三层模型分级** | 60-80% | 中 | P0 | 核心架构决策，MVP 必须 |
| **Batch API** | 50% | 低 | P0 | OpenAI 官方支持，简单集成 |
| **Prompt Cache** | 10-30% | 低 | P0 | 同场景 Agent 共享 system prompt |
| **语义缓存** | 20-40% | 中 | P1 | Agent 常见回复模式缓存 |
| **Early Stopping** | 10-30% | 中 | P1 | 收敛检测提前结束 |
| **Token 预算管理** | 防失控 | 低 | P0 | 每次模拟设 token 上限 |

### 5.5 Pipeline 成本分布

五阶段管线中，成本主要集中在模拟阶段：

```
Stage 1 — 图谱构建:     5-10%  ████
Stage 2 — Agent生成:    5-10%  ████
Stage 3 — 模拟执行:    70-80%  ████████████████████████████████
Stage 4 — 报告生成:     5-10%  ████
Stage 5 — 深度交互:     < 5%   ██
```

### 5.6 Replit 原型的定位说明

> ⚠️ **重要澄清**：Replit 原型是一个**纯 UI 演示原型（高保真 mockup）**，不包含任何真实的模拟引擎或 LLM 集成。
> 详细源码分析见 `reference/platform-source/README.md`。

Replit 原型的实际技术实现：
- **无 Agent 模拟引擎**："运行模拟" 按钮的后端逻辑是 `setTimeout(3000)` + `Math.random()` 生成随机指标
- **数据全部预置**：seed.ts 通过 SQL INSERT 写入约 90 条演示记录，包括硬编码的 "487 次交互" 字符串
- **零 AI 依赖**：package.json 中无 OpenAI SDK、无 langchain、无任何 LLM/模拟库
- **纯 CRUD 后端**：所有 API（约 20 个端点）仅执行 SELECT/INSERT，无业务计算

Replit 原型的实际价值：
- ✅ 验证了 **14 个模块的信息架构与用户流程**设计
- ✅ 验证了 **8 种 Agent 模板的数据模型定义**（schema 设计合理，字段覆盖全面）
- ✅ 提供了 **完整的 UI 参考**，可直接指导前端开发
- ❌ 未验证模拟性能、Agent 交互质量、LLM 调用成本等技术指标

因此，模拟性能基准需要在集成 OASIS 引擎后通过实际运行来建立。基于 §5.3 的理论估算，200 Agent × 50 轮的模拟在 200 并发下预计可在 1 分钟内完成。

### 5.7 Agent-Kernel 源码验证的成本与并行模型

基于 Agent-Kernel 源码（`EasyPlanPlugin.py`、`agent_manager.py`、`pod_manager.py`、`async_router.py`）的逐文件分析，为 BizSim 的成本估算提供了实测参考数据。

#### 5.7.1 单 Agent 单 tick LLM 开销（源码实测）

Agent-Kernel 的 Agent 每 tick 执行 5 个组件（perceive → plan → invoke → state → reflect），其中 LLM 调用集中在 plan 和 reflect：

| 组件 | LLM 调用 | Prompt 构成 | Token 消耗（估算） |
|------|---------|-----------|------------------|
| perceive | 0 次 | — | 0 |
| plan | **1 次** | 周围 Agent JSON + 位置 + 历史 + 动作空间 + 格式示例 | 输入 ~200-400，输出 ~50-200 |
| invoke | 0 次 | — | 0 |
| state | 0 次 | — | 0 |
| reflect | **0-1 次** | 可选，条件触发 | 输入 ~300-500，输出 ~100-300 |

**单 Agent 单 tick 总计**：1-2 次 LLM 调用，~250-900 tokens/tick。

**与 §5.2 的对比**：§5.2 假设每 Agent 每轮 2,700 tokens（输入 2,500 + 输出 200），是基于 OASIS 社交媒体场景（帖子全文 + 历史线程）的上界估计。BizSim 的商业讨论场景更接近 Agent-Kernel 的量级（~400-900 tokens），因为商业动作空间更结构化、Agent 发言更短。实际成本预计比 §5.2 估算**低 50-70%**。

#### 5.7.2 并行开销实测模型

**单机模式 (asyncio.gather)**：

```
1 tick 时间 ≈ max(单次 LLM 延迟, N_agents / API_RPM × 60s)
            ≈ max(0.5-2s, N / RPM × 60)
```

- N=50, RPM=500 (GPT-4o-mini tier-3)：tick ≈ max(1s, 6s) ≈ 6s
- N=200, RPM=500：tick ≈ max(1s, 24s) ≈ 24s
- N=200, RPM=10000 (GPT-4o-mini tier-5)：tick ≈ max(1s, 1.2s) ≈ 1.5s

asyncio.gather 的实际开销极低（微秒级调度），瓶颈完全在 LLM API 吞吐量。

**分布式模式 (Ray Actor)**：

Agent-Kernel 的 PodManager 将 Agent 分配到多个 @ray.remote MasPod，每 Pod 默认 5 Agent。分布式开销：

| 开销项 | 量级 | 说明 |
|-------|------|------|
| Ray Actor 创建 | ~50-100ms/pod | 一次性开销，PodManager 批量初始化 |
| Pod 间 RPC (`forward.remote`) | ~1-5ms/次 | Ray 共享内存序列化 |
| Pod 内 asyncio.gather | ~0μs 调度 | 与单机模式相同 |
| 各 Pod 独立 HTTP Session | 无额外开销 | 每 Pod 自己的 aiohttp.ClientSession |
| psutil 内存监控 | ~1ms/次 | MasPod 内置 `process.memory_info().rss` |

**分布式扩展效果**：

```
单机 200 Agent × 50 ticks, RPM=500:
  tick ≈ 24s → 总耗时 ≈ 20 分钟

4 节点分布式 (每节点 50 Agent, 独立 API key, 各 RPM=500):
  tick ≈ 6s → 总耗时 ≈ 5 分钟

单机高配 RPM=10000:
  tick ≈ 1.5s → 总耗时 ≈ 75 秒
```

> **结论**：对于 BizSim MVP（≤200 Agent），单机 asyncio + 高 RPM tier 完全足够。分布式 Ray 是 Enterprise 模式（500+ Agent）的扩展路径。

#### 5.7.3 三引擎并行开销对比

| 维度 | OASIS | Agent-Kernel | BizSim 取用 |
|------|-------|-------------|-------------|
| **每 Agent 每 tick LLM 调用** | 1 次 | 1-2 次 | 1 次（plan only，MVP 不做 reflect） |
| **Token 消耗/次** | ~2,700 (社交全文) | ~250-600 (结构化) | ~400-900 (商业讨论) |
| **Agent 间并行** | asyncio.gather | asyncio.gather + Ray | asyncio.gather（MVP）|
| **交互选择** | O(n×k) 推荐算法 | O(n) 全连接 | O(n×k)（复用 OASIS 推荐） |
| **真正瓶颈** | LLM API RPM | LLM API RPM | LLM API RPM |
| **状态持久化开销** | 无 | ~5-10ms/agent (DB write) | P2 引入 |
| **内存占用/Agent** | ~1-5 MB | ~2-8 MB (含 plugin 上下文) | ~2-5 MB（目标） |

#### 5.7.4 修正后的 BizSim 成本估算

综合 Agent-Kernel 源码验证和 OASIS 推荐算法，修正 §5.2 的成本模型：

| 场景 | Agent 数 | 轮次 | LLM 调用/tick | 总 LLM 调用 | Token (avg) | GPT-4o-mini 成本 | 混合分级成本 |
